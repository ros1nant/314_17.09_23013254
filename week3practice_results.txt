# Part 2: The Synchronization Trap

| Method                   | Pi       | Runtime  |
| ------------------------ | -------- | -------- |
| Single-threaded          | 3.141746 | 5.9763 s |
| Synchronized (4 threads) | 3.141654 | 9.8793 s |

**Slowdown multiplier:** 1.65x

**Observation:** The synchronized version was slower than the single-threaded version because frequent lock acquisition and release caused synchronization overhead. In CPython, the GIL also limits the benefits of CPU-bound threading.

## Questions

### 1. Why did 16 threads not run twice as fast as 8 threads?

Increasing the number of threads from 8 to 16 improved runtime only slightly, from 3378.80 ms to 3302.71 ms. This happened because of process creation overhead, CPU resource limitations, and scheduling overhead. Additional threads do not always provide proportional speedup.

### 2. Why was the synchronized version slower than one single core?

The synchronized version required a lock for every shared counter increment. This created frequent lock contention and synchronization overhead. In addition, Python's GIL limits parallel execution of CPU-bound threads, making the synchronized version slower than the single-threaded loop.
